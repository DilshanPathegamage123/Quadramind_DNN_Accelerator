multi_dnn_top: how data and control actually flow

One scheduler, one accelerator core, and a three-state dispatch FSM between them. This walks the path from a task arriving at the scheduler to bytes leaving DRAM and results landing in the array — and marks the places where the RTL differs from what the comments claim.

00

Three planes, colour-coded throughout

Every diagram below uses the same three colours. Keeping them apart is the whole trick to reading this design: the schedulers never touch a byte of tensor data, and the data plane never sees a task ID.

Data plane

Tensor bytes. DRAM → AXI → scratchpad banks → fetchers → PE array. Carries no scheduling identity at all.

Control plane

Single-cycle strobes. start, phase_mem_done, phase_compute_done, done — the handshake that closes the loop back to the scheduler.

Scheduling plane

Task descriptors and the compiler-built scheduling table. Layer IDs, DNN IDs, cycle estimates, memory footprints, batch sizes.

01

Top-level flow

The host (a cocotb testbench, or the Python harness) feeds two entirely separate front doors. Basic tasks go in through a FIFO-style task port; DNN-aware schedulers get a scheduling table written a row at a time before the run starts. scheduler_select decides which door is live.

02

The dispatch handshake, cycle by cycle

The dispatch FSM is the only thing standing between the two worlds. It is deliberately tiny — three states, all pulses defaulted low each cycle and asserted for exactly one clock.

  1. D_IDLEWaits for sched_out.valid. On assertion it latches task_or_layer_id into current_layer_id and dnn_id into current_dnn_id, raises sdt_start for one cycle, and moves to D_RUN.
  2. D_RUNWatches two strobes coming back from single_dnn_top. phase_mem_done is re-emitted as mem_access_done; phase_compute_done becomes compute_done. Both go only to the DNN-aware family — the wrapper masks them off below scheduler_select == 11.
  3. D_RUNWhen sdt_done arrives (the accelerator hit S_FINAL), it advances to D_WAIT_DONE.
  4. D_WAITPulses task_complete back into the basic scheduler — which is what retires the queue entry and bumps total_tasks_processed — plus task_complete_pulse out to the testbench. Then straight back to D_IDLE.

03

Inside single_dnn_top: the split-FSM

The reason the accelerator core exposes two done strobes instead of one is entirely for the schedulers' benefit. AI-MT and the BatchDNN family need to know when the memory half of a layer has retired, independently of the compute half, so they can overlap the next layer's fetch with the current layer's MACs.

Because S_MEM only exits on pf_done, the memory-phase duration that a DNN-aware scheduler observes is not a constant. It varies with mem_layout, casting scheme, and tile geometry, because the prefetcher walks the layer's weight and input tiles in fetch order through the layout-dependent address mapping. That is what makes memory/compute balancing in AI-MT mean anything.

04

Where the bytes actually move

This is the part most easily misread from the block diagram. There are two distinct memory paths inside single_dnn_top, and they serve different purposes.

PathCarriesPurpose
layout_prefetcher → AXI Real burst reads for the layer's weight + input tiles Generates the off-chip traffic and the timing of the memory phase. Shares the AXI master with the stamp backend through a fixed-priority mux; they never overlap because the walk starts only after the stamp phase completes.
mem_backend_wrap → scratchpad_ram Delta-ops (STAMP) or page-table translations (PAGED); banked SRAM reads Models on-chip capacity, replacement behaviour, and bank conflicts. Its rd_en is driven from the debug port, wr_en is tied to zero — this backend is a timing and statistics model, not the operand feed.
ext_* ports Operands into the PE array and results back out The actual compute data plane. Shape depends on dataflow: WS uses a 2-D weight port and a 1-D output port; OS and IS are the inverse. systolic_array_wrap exposes the union and ties off the unused flavour.

Bank conflicts surface as three counters that climb all the way to the top: bank_conflict_detected pulses whenever at least one port stalls, stats_bank_conflicts counts events, and stats_bank_conflict_stall_cycles accumulates stalled port-cycles. Under NUM_BANKS ≥ 2 the low-order address bits pick the bank and the lower-indexed port wins a collision; the loser gets rd_valid = 0 and retries next cycle.

All eleven are instantiated in parallel and fed the same queue inputs; the select line only chooses whose outputs are believed. For these schedulers the memory phase is invisible — the dispatch FSM's mem_access_done pulse is masked off, and only the end-to-end done closes the loop.

All three are elaborated inside dnn_scheduler_wrapper, and the mem_access_done/compute_done strobes are gated per-instance so only the selected scheduler advances. The scheduling-table write port is likewise gated by st_write_en && (dnn_scheduler_select == n) — load the table after setting the select line, or it lands in the wrong scheduler.

07

Implementation notes worth knowing

Three places where the current RTL behaves differently from what the surrounding comments suggest. None are fatal, but they change how you interpret results.

The dispatch FSM ignores is_compute_task

The tagged union carries is_compute_task, and both the package comment and the wrapper comment say the dispatch FSM uses it to drive "a memory-only phase or a compute phase". It does not — D_IDLE latches on sched_out.valid alone and always runs the full S_MEM → S_COMPUTE → S_FINAL sequence. So an MT and a CT dispatch cost the same in the RTL, and the memory/compute overlap the schedulers reason about is modelled in the scheduler's own counters rather than realised in the datapath.

ct_batch_size is observed, not applied

multi_dnn_top declares ct_batch_size and wires it out of the scheduler wrapper, but nothing downstream consumes it. BatchDNN's split/merge decisions therefore affect scheduler-side statistics and issue order, not the tile geometry handed to single_dnn_top — that comes from the cfg_* ports the host drives directly.

CT wins over MT in the mux

When a DNN-aware scheduler raises ct_valid and mt_valid in the same cycle, the union mux takes the compute task. The memory task is not lost — it simply waits — but under a fully-backed-up CT queue the MT stream can be deferred for a long stretch.

09

The Python layer above it

Nothing in the RTL knows a scheduler by name. SimConfig.scheduler holds a string from a fourteen-entry list, and scheduler_select() turns it into the integer that reaches the scheduler_select port — via -GNAME=value overrides when Verilator is present, or the SIM_SCHEDULER environment variable that the cocotb testbench reads. With neither toolchain installed the runner falls back to the NumPy reference model, which reproduces the same accounting without elaborating any of this.
