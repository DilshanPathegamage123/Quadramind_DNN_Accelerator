CLAIM

What is new here

Conventional accelerators keep a runtime structure — a tag array or a page table — to record where each tile currently lives on-chip. That structure costs area, adds a translation step to every access, and places tiles at addresses the compiler cannot predict.

The stamp scheme removes it. Because a DNN's execution schedule is fully known at compile time, the compiler can compute the complete on-chip layout for every phase in advance, diff consecutive layouts, and emit the exact list of operations needed to turn one into the next. The hardware becomes a small sequencer with no tags, no translation, and no lookup.

MECHANISM

How a phase transition is resolved

A stamp is the complete scratchpad layout for one execution phase. A delta is the difference between two consecutive stamps. The compiler classifies every byte of the next stamp into one of five operations, and only one of them touches DRAM.

Worked example — phase 0 → phase 1, taken verbatim from stamp_metadata.json

  1. MOVE input tile 768 B

    Still on-chip, needs relocating. Scratchpad read + write.

  2. LOAD input tile 1,280 B

    Genuinely new data. The only op that touches DRAM.

  3. ZERO input tile 256 B

    Padding halo. Written as zeros, never fetched.

  4. ALLOC output tile 256 B

    Output slot. The array writes it; no memory traffic.

  5. KEEP weight tile 2,304 B

    Already at the right address. Costs nothing.

Working set 4,864 B  →  fetched from DRAM 1,280 B (26%). The other 74% never leaves the chip.

The weight tile is kept because this transition slides the output window sideways within the same output-channel slice — the filters are unchanged, so re-fetching them would be pure waste. A page table cannot make that deduction; it only knows a page is resident, not why.
VERIFY

Three independent implementations, one answer

The strongest evidence that the scheme is real is that three separately written implementations of it agree exactly: the Python compiler's own bookkeeping, an independent cycle-accurate model of the controller FSM, and the SystemVerilog hardware itself running in Vivado.

LIMITS

What this does not yet show

Stating the boundary honestly is part of the result. Three things are open:

Metadata RAM scales with phase count

A 128-phase layer compiles to 572 delta operations. At 128 bits each that is 8.9 KB of metadata for a 16 KB scratchpad. This is the real cost of removing the tag array, and it is the scheme's main scaling limit.

Paged wins on raw beats for small layers

Page faulting pulls whole 4 KB pages, which for a small working set moves fewer total beats than fine-grained delta fetching. The stamp scheme's advantage is in conflicts, translation cost and predictability — not in every metric at every size.

Two stamp op-stream generators still exist

The integrated cocotb test builds its own load/keep stream rather than consuming delta_ops.hex. The standalone compiler-to-RTL path is fully closed; wiring the integrated path to the same file is the next step.

Single layer geometry

Results are for a 16×14×14 → 32-channel 3×3 padded convolution on a 16 KB scratchpad. Sweeping layer shape and scratchpad size is the remaining characterisation work.
