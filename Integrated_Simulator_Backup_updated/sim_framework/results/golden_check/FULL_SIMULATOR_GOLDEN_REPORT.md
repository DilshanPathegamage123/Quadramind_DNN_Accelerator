# Full-Simulator Golden-Reference Correctness Report

**Date:** 2026-07-13
**Method:** RTL simulated entirely in software with Verilator 5.050 + cocotb 2.0.1
(no FPGA). Golden references generated by TensorFlow 2.21.0 forward passes.
**Pass criterion:** every output element within **5% of full scale**
(5% × max|expected| per layer). Every number in this report was measured from
a real Verilator simulation of the RTL in `sim_framework/rtl/`; nothing is
estimated or extrapolated unless explicitly labelled as the Python model's
estimate.

## 2. Golden references (Step 2)

`models/dump_tf_model.py` was run for both small golden workloads; each layer
directory contains `expected.npy` + `config.json` (+ inputs/weights/quant):

| Model | Layers | Shapes |
|---|---|---|
| tiny_cnn | 2 | Conv 3×3 (8×8×3 → 6×6×8), Dense 288→4 |
| mnist_cnn | 3 | Conv 3×3 ReLU (28×28×1 → 26×26×8), Conv 3×3 ReLU (13×13×8 → 11×11×16), Dense 1936→10 |

The mnist conv layers include ReLU in `expected.npy`; the comparison applies
ReLU to the dequantized RTL output for those layers (the array computes the
raw convolution; the activation is not array hardware).

**Fixed-point encoding used for the RTL runs:** Q?.14 inputs and weights
(14 fractional bits each), products/accumulator at 28 fractional bits.
The dump's default 28/31-bit encodings would overflow the 48-bit accumulator
and the 32-bit writeback slice; the golden itself is unchanged (`expected.npy`).

## 3. Single-DNN correctness, 8×8 array, OS dataflow (Step 3)

Harness: `tb/golden/run_golden.py` + `tb/golden/test_golden_single.py` stream
the quantized TF tensors onto `single_dnn_top`'s `ext_*` behavioural-memory
ports and capture the writeback. One `start` pulse computes one output pixel
across up to 8 output channels through array column 0 (see finding F1 for why
only column 0 is usable).

| Layer | Invocations | RTL cycles | Max err (%FS) | Mean err (%FS) | Verdict |
|---|---|---|---|---|---|
| tiny_cnn L0 (conv) | 36 | 9,504 | 0.013 | 0.0035 | **PASS** |
| tiny_cnn L1 (dense) | 1 | 2,613 | 0.017 | 0.0060 | **PASS** |
| mnist_cnn L0 (conv+ReLU) | 676 | 68,952 | 0.009 | 0.0009 | **PASS** |
| mnist_cnn L1 (conv+ReLU) | 242 | 161,898 | 0.019 | 0.0022 | **PASS** |
| mnist_cnn L2 (dense) | 2 | 34,890 | 0.050 | 0.0213 | **PASS** |

**5/5 layers pass at ≤0.05% of full scale** — three orders of magnitude below
the 5% gate; the residual is pure Q14 quantization noise. During debugging,
tiny_cnn L0 channels 0–6 were additionally verified **integer-exact** (252/252
elements) against a fixed-point software convolution of the same quantized
tensors.

### Options that could NOT be run (and why)

- **Casting schemes (unicast / multicast / hybrid):** no such configuration
  knob exists anywhere in the RTL, `SimConfig`, or the config files. The only
  "broadcast" in the codebase is WS's inherent horizontal broadcast. Nothing
  to simulate.
- **Memory-management schemes (static / double-buffer / unified-buffer /
  cache-based):** these exist only as *analytical model factors* in
  `scripts/run_full_eval.py` (`MEMSCHEME_MODEL`); there is no RTL implementing
  them. The real hardware axis is the STAMP vs PAGED backend, and both pass.
- **`num_banks`:** documented as a knob, but `single_dnn_top` does not expose
  a `NUM_BANKS` parameter (it is not plumbed from the top to
  `mem_backend_wrap`), so `-GNUM_BANKS` fails at the Verilator command line.
  All runs used the RTL default.

## 5. Multi-DNN correctness under schedulers (Step 5)

Harness: `tb/golden/run_golden_multi.py` + `test_golden_multi.py` on
`multi_dnn_top` (OS, 8×8). Mix of three DNN tasks: tiny_cnn conv pixel (0,0),
mnist_cnn conv pixel (1,1) (ReLU), tiny_cnn dense pixel — each dispatched by
the scheduler RTL, config supplied reactively per dispatched task.

| Scheduler | Dispatch order | Per-task max err (%FS) | Verdict |
|---|---|---|---|
| FIFO | 0 → 1 → 2 | 0.010 / 0.004 / 0.017 | **PASS** |
| LIFO | 2 → 1 → 0 | 0.010 / 0.004 / 0.017 | **PASS** |
| AI-MT | 0 → 1 → 2 | 0.010 / 0.004 / 0.017 | **PASS** |
| BatchDNN | 0 → 1 → 2 | 0.010 / 0.004 / 0.017 | **PASS** |
| BatchDNN++ | 0 → 1 → 2 | 0.010 / 0.004 / 0.017 | **PASS** |

Every DNN produces its correct golden output under every scheduler, and the
errors are **byte-identical across schedulers** while LIFO demonstrably
reverses the execution order — the schedulers change ordering only, never
results. (Workarounds F6/F7 below were needed to make the DNN-aware
schedulers dispatch at all.)

## 6. Estimated vs actual cycles (Step 6)

Full data: `results/golden_check/estimated_vs_actual_cycles.csv` (16 rows).
"Estimated" = `pysim/software_ref.py::estimate_cycles` (the Python model);
"actual" = RTL cycle counts measured by cocotb in the correctness runs above.

| Run | Est (Python) | Actual RTL total | Invocations | Agreement |
|---|---|---|---|---|
| tiny_00 OS | 48 | 9,504 | 36 | 0.51% |
| tiny_01 OS | 309 | 2,613 | 1 | 11.8% |
| mnist_00 OS | 120 | 68,952 | 676 | 0.17% |
| mnist_01 OS | 165 | 161,898 | 242 | 0.10% |
| mnist_02 OS | 1,957 | 34,890 | 2 | 5.6% |
| tiny_00 IS | 68 | 1,337,472 | 7,776 | 0.01% |
| tiny_00 WS (8×1) | 140 | 24,192 | 864 | 0.58% |
| multi mixes (5 scheds) | 477 | 2,984–2,986 | 3 tasks | ~16% |

**Honest interpretation:** agreement is poor (0.01%–16%), and the cause is
structural, not noise. The Python model estimates a *single idealized
full-array pass* per layer (all H×W PEs computing in parallel). The RTL, as
built, can only produce verified-correct results through array column 0 (one
output pixel per pass for OS — finding F1), so the measured runs necessarily
execute OH×OW(×K/H) sequential passes. The per-invocation actuals
(102–670 cycles for conv invocations) are the RTL's true cost of one
column-0 pass including weight preload, streaming, and writeback — a
quantity the Python model does not represent. Until finding F1 is fixed in
RTL, the estimate and the hardware measure different execution schemes, and
reporting a high "agreement" number would be misleading.

## 7. RTL findings

### Compile fixes applied (syntax/tool-compatibility only, no behavior change)

1. `batchdnn_pp_scheduler.sv`: variable named `dist` — a reserved SV keyword —
   renamed `dist_val`.
2. `batchdnn_pp_scheduler.sv`: two bare `return;` in a value-returning
   function → `return find_bottleneck;` (value already assigned).
3. `batchdnn_scheduler.sv` / `batchdnn_pp_scheduler.sv`: nonblocking
   assignments to `automatic` locals (illegal, IEEE 1800 §6.21) → blocking;
   surrounding code only makes algorithmic sense with immediate update.
4. `multi_scheduler_wrapper.sv`: `task_stats_t` made `packed` (Verilator
   cannot do NBA to unpacked-struct arrays; statistics bookkeeping only).
5. `sim_framework_pkg.sv`: `SCHED_*` localparams renamed `SCHEDSEL_*` — the
   original names collide with glibc `<sched.h>` macros in Verilator's
   generated C++.

### Functional findings (NOT fixed — verified empirically, worked around in the testbench)

- **F1 — `pe_enable <= '{default:1'b1}` on a packed 2-D array** (OS and WS
  tops) sets each row to `2'b01`, enabling **only column 0** of the array.
  Fix would be `'1`. Verified: Verilator trace shows `pe_enable=0x5555` (8×2).
- **F2 — WS writeback reads the rightmost PE column** (`pe_result[r][W-1]`),
  which F1 permanently disables for any `ARRAY_WIDTH>1` → WS output is
  structurally zero at 8×2 and 8×8 (measured identical all-zero results).
  WS is functional only at `ARRAY_WIDTH=1`, where it computes the full
  per-channel kernel window in hardware and passes at 0.013%.
- **F3 — IS enable window:** `pe_enable` is combinationally tied to the
  ~3-cycle `WAIT_WEIGHTS` state while weight pulses ripple one column/cycle;
  columns 1–2 fall in the FSM gap (0/3888 correct in probe) and the last
  weight iteration's window closes before column 0's accumulate. The IS
  stationary-input register is also not reloadable during weight streaming,
  so multi-tuple accumulation is architecturally absent. IS verified at
  single-MAC granularity through column 0 (all 27 tuples integer-exact).
- **F4 — IS final load window:** a data response on the last LOAD_INPUTS
  iteration is not honoured (probe isolated exactly `t_load = C·KH·KW−1`);
  the harness serves that tuple predictively one cycle early.
- **F5 — OS enable shutdown race:** the last row's final MAC lands exactly on
  the cycle `pe_enable` drops after `input_fetch_done`; without 2-cycle-early
  streaming the last product of row H−1 is silently dropped (tiny_00 ch 7
  matched a "drop-last-term" model on all 36 pixels).
- **F6 — Scheduler select mapping:** `unified_scheduler_wrapper` passes
  `scheduler_select[1:0]` (not `select−11`) to `dnn_scheduler_wrapper`. So
  select 11 ("AI-MT") muxes BatchDNN++ **but** the st-write gate compares
  `==2'd2`, making select 11 unusable; AI-MT actually runs at select 12,
  BatchDNN at 13, BatchDNN++ at 14. The tests compensate accordingly.
- **F7 — AI-MT/BatchDNN++ queue registers multi-driven:** the MT candidate
  queue is enqueued in one `always_ff` and popped in another; a same-edge
  enqueue+pop loses the enqueue (observed: third table row vanished,
  `mt_cq_cnt` never exceeded 1). Worked around by spacing table writes.
  Also, AI-MT's balance check (`mem_cycles <= compute_cycle_ctr`, init 0)
  can never admit a first MT with nonzero `st_mem_cycles`.

## 8. Changes made to the repository during this task

**No functional implementation of the simulator was changed.** Every datapath
element whose correctness this report certifies — PEs, systolic arrays,
fetchers, address generators, memory backends, tops, scheduler algorithms,
and the Python model (`pysim/`) — ran exactly as found in the repo. All
functional defects discovered (F1–F7 above) were deliberately **left in
place** and worked around in the testbench, so the measured results describe
the hardware as it exists today.

Three categories of changes were made:

### 8.1 RTL edits — compile compatibility only (5 edits, 4 files)

These were required for Verilator 5.050 to compile the design at all; each
preserves the original logic. Without them, nothing in this report could
have been simulated.

| File | Edit | Why |
|---|---|---|
| `rtl/schedulers/batchdnn_pp_scheduler.sv` | variable `dist` → `dist_val` | `dist` is a reserved SystemVerilog keyword (constraint operator); Verilator rejects it as a syntax error. Pure rename. |
| `rtl/schedulers/batchdnn_pp_scheduler.sv` | two bare `return;` → `return find_bottleneck;` | Bare `return` inside a value-returning function is rejected; the return variable was already assigned on the lines above, so the returned value is identical. |
| `rtl/schedulers/batchdnn_scheduler.sv`, `batchdnn_pp_scheduler.sv` | nonblocking `<=` → blocking `=` on the `automatic` locals `req_batch`/`merged` | NBA to automatic variables is illegal (IEEE 1800 §6.21) — the original code could not be compiled by any conforming tool, so it had no well-defined behavior to preserve. Blocking assignment matches the documented sub-batch merge algorithm (later lines in the same block read the merged value). Statement order was kept so all register (`<=`) updates still see the pre-merge value where they did before. |
| `rtl/schedulers/multi_scheduler_wrapper.sv` | `task_stats_t` → `struct packed` | Verilator cannot synthesize NBA to arrays of unpacked structs inside loops. The struct holds wait/turnaround statistics bookkeeping only; packing changes memory layout, not values. |
| `rtl/pkg/sim_framework_pkg.sv` | localparams `SCHED_*` → `SCHEDSEL_*` | The names collide with glibc `<sched.h>` macros (`SCHED_FIFO`, `SCHED_RR`, …) in Verilator's generated C++, which macro-expand to integers and break compilation. These localparams are referenced nowhere else in the RTL (checked by grep), so the rename is inert. |

### 8.2 New files added (nothing existing overwritten)

  golden harness (OS/IS/WS data serving, capture, comparison).

## 10. Verdict

- **Golden correctness at the 5% tolerance: PASS** for all 5 layers of both
  golden models on the OS 8×8 configuration, all three memory layouts, both
  memory backends, and all five schedulers in the multi-DNN mix — with
  measured errors ≤0.05% of full scale (quantization-limited).
- **IS** passes at single-MAC granularity and **WS** passes at width 1;
  neither can compute a full multi-channel convolution in hardware as
  currently written (findings F1–F3) — those are RTL limitations, not
  tolerance failures.
- **Casting schemes and the four memory-management schemes do not exist in
  the RTL** and therefore could not be (and were not) simulated.
- **Cycle fidelity between the Python model and the RTL is low** (0.01–16%
  agreement) for the structural reasons in §6; the CSV contains the exact
  measured numbers.
